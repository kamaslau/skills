# UTF-8 字节区间与字符语种判定

本文回答两个问题：

1. 「判断字符语种」能否基于 UTF-8 的编码段区间？
2. 若能，和现在按码点（UTF-16）判定相比该怎么选？

结论先行：**能，且在数学上与按码点判定等价；但在 Node.js 中应当继续用码点判定，字节区间留给面向字节的流水线。**

---

## 1. 为什么两者等价

UTF-8 是**保序前缀码**（order-preserving prefix code）：

- 码点 `cp₁ < cp₂` ⟺ 其 UTF-8 字节序列按字典序比较 `bytes(cp₁) < bytes(cp₂)`。
- 任一合法 UTF-8 序列都不是另一合法序列的前缀（1 字节序列取值 `0x00–0x7F`，多字节序列首字节 `0xC2–0xF4`，两者不相交）。

「不是前缀」这一点很关键：它保证比较不会在长短序列之间出错，字典序比较因此严格等价于数值比较。

推论：**一个码点区间 `[a, b]` 与一个字节区间 `[bytes(a), bytes(b)]` 一一对应**。所以「字节落在 `[E4 B8 80, E9 BF BF]` 内」与「码点在 `[U+4E00, U+9FFF]` 内」是同一个判定，只是表示形式不同。

本仓库有回归用例直接断言这一点（`scripts/selftest.mjs`）：对所有收录区间的端点与中点采样，验证 `Buffer.compare(bytes(a), bytes(b))` 的符号与 `a - b` 一致。

## 2. 字节区间的粗粒度用法：只看 lead byte

UTF-8 的首字节（lead byte）已经能给出粗粒度分区，代价是精度：

| lead byte | 覆盖的码点范围 | 大致语种 |
| --- | --- | --- |
| `0x00–0x7F` | U+0000–U+007F | ASCII |
| `0xC2–0xDF` | U+0080–U+07FF | 拉丁扩展、希腊、西里尔、希伯来、阿拉伯、泰文等 |
| `0xE0–0xEF` | U+0800–U+FFFF | BMP 其余：CJK、假名、谚文、全角形式 |
| `0xF0–0xF4` | U+10000–U+10FFFF | 增补平面：CJK 扩展 B+、emoji |

再加第 2 个字节可精确到「块」级别，例如：

- 假名 U+3040–U+30FF → `E3 81 80 … E3 83 BF`（lead `0xE3`，次字节 `0x81–0x83`）
- 全角形式 U+FF00–U+FFEF → `EF BC 80 … EF BF AF`（lead `0xEF`）
- CJK 基本汉字 U+4E00–U+9FFF → `E4 B8 80 … E9 BF BF`（lead `0xE4–0xE9`）
- 谚文音节 U+AC00–U+D7AF → `EA B0 80 … ED 9E AF`（lead `0xEA–0xED`）

**陷阱：区间会跨 lead byte 边界，单看 lead byte 不够。** CJK 扩展 A（U+3400–U+4DBF）的字节区间是 `E3 90 80 … E4 B6 BF`，CJK 基本汉字是 `E4 B8 80 … E9 BF BF`——两者都在 `0xE4` 上有分布，`lead == 0xE4` 无法区分「扩展 A 的尾部」与「基本汉字的开头」。用例 `lead byte 粗分（端点区间）` 正是断言这一重叠确实存在，提醒不要只用 lead byte 下结论。

另一个陷阱：**必须先定位 lead byte 再取序列**。UTF-8 有自同步性（continuation byte 恒为 `0x80–0xBF`，与 lead byte 取值不相交），所以从任意 lead byte 边界开始扫描是安全的；但绝不能「只看某个字节的值落在某区间就判定」——多字节字符的中间字节会落在别的块区间里造成误判（例如 `0xBF` 同时出现在谚文、CJK 基本汉字与全角形式的字节序列中）。

## 4. 为什么本工具仍然按码点判定

- **JS 字符串是 UTF-16。** 要拿到字节必须先 `TextEncoder.encode()`，等于为一次判定多一次编码与内存分配；而 `charCodeAt()` 是 O(1)。本工具对每个字符都要判定（CJK 上下文、假名、谚文、全角数字/字母），热路径上不该付这个代价。
- 两者判定结果完全相同（第 1 节的等价性），既然如此就选便宜的那个。

真正应当按**字节**判定的场景是：

1. **面向字节的流水线**——Go / Rust / C 里字符串本质是字节切片，直接比字节区间是自然的写法；
2. **流式扫描**——不必解码成码点即可过滤（利用自同步性从 lead byte 起跳）；
3. **编码未知时的原始字节分析**——见下节，此时根本还没解码，只能看字节。

## 5. 另一个层次的问题：判定「编码」必须用字节

「语种」与「编码」是两个不同层次的问题：

- **语种判定**：编码已知、字符已解码 → 码点与字节区间等价，随意选。
- **编码判定**：编码未知、尚未解码 → **只能**看字节模式，因为根本没有码点可用。

本工具的输入编码探测（`scripts/encoding.mjs`）正是后者，顺序为：

1. **BOM**：`EF BB BF` → UTF-8；`FF FE` → UTF-16LE；`FE FF` → UTF-16BE。置信度 high。
2. **严格 UTF-8 合法性**：用 `TextDecoder('utf-8', { fatal: true })` 解码，任一字节序列非法即抛错。能过这一关的就是 UTF-8。置信度 high。
3. **UTF-16 空字节模式**：无 BOM 时，UTF-16 中的 ASCII 字符必有一半是 `0x00`（LE 为 `41 00`，BE 为 `00 41`）。统计预期位置为 0 的比例，>0.25 判为 UTF-16。置信度 medium/low。
4. **legacy 双字节字频打分**：GB18030 / Big5 / EUC-KR / Shift_JIS 各解码一遍，按「高频汉字命中 +4、平假名 +3、谚文 +3、片假名 +2、半角片假名 −2、U+FFFD 与控制字符 −8」打分取最优。

第 4 步里 **半角片假名 −2** 这条是关键：Shift_JIS 的 `0xA1–0xDF` 是单字节半角片假名区，几乎任何字节流被按 Shift_JIS 解码都会造出成片半角片假名；而正常日文正文不会出现这种分布。不加这条惩罚时，GB18030 与 Big5 样本会被误判成 Shift_JIS（实测过）。置信度非 high 时，`--report` 会额外打印一行 `[warn]` 提示可用 `--input-encoding` 覆盖。

## 6. 与输出约定的关系

因为输入编码不定、输出恒为 UTF-8，上述探测是**必需**而非锦上添花：若直接把 GB18030 的字节当 UTF-8 解码，会得到 U+FFFD 乱码，规范化再正确也是「乱码进、乱码出」。

输出侧固定三件事：

- 编码一律 UTF-8（`--bom keep|strip|add` 控制 BOM，默认沿用输入）；
- 扩展名一律 `.md`（`-o` 替换扩展名，`--suffix` 保留后缀再追加 `.md`）；
- 文件以单个换行结尾，且沿用正文既有行尾风格（LF / CRLF 不被改写）。
